# 数据库

## Mysql & Sqlserver

### 概念

::: tip 什么是数据库什么是SQL

- 数据库是一个长期存储、有组织的数据集合，可以高效地对数据进行 存储、管理、查询和维护。
- SQL（Structured Query Language） 是 结构化查询语言，专门用于操作关系型数据库。
  - DDL（数据定义语言）：定义数据库对象
    - CREATE、ALTER、DROP
  - DML（数据操作语言）：操作表中数据
    - INSERT、UPDATE、DELETE
  - DQL（数据查询语言）：查询数据
    - SELECT、WHERE、GROUP BY、DISTINCT、ORDER BY、JOIN
  - DCL（数据控制语言）：权限管理
    - GRANT、REVOKE
  - TCL（事务控制语言）：事务管理
    - COMMIT、ROLLBACK、SAVEPOINT

:::

::: tip 常见的数据库类型有哪些？

关系型、非关系型数据库、时序数据库、图数据库。

最常用的是关系型数据库，MySql，SqlServer。

可以考虑使用图数据库做路径算法。

> Neo4j 提供了图算法库，可以直接使用图数据库来执行各种图算法，例如最短路径、社区检测等。如Google Maps使用图数据库技术来计算最短路径

:::

::: tip 什么是范式？常见的范式有哪几种？

范式（Normalization / Normal Form） 是一套规则，用来约束表结构，减少数据冗余、避免数据异常、提高一致性。

- 1NF：字段不可再分。
- 2NF：消除部分依赖。
- 3NF：消除传递依赖。
- BCNF：在 3NF 基础上进一步消除候选键异常依赖。
- 4NF：消除多值依赖。
- 5NF：消除连接依赖。


但业务场景中设计到 第三范式 就够了，实际应用中为了效率，比如报表计算等，通常会增加冗余字段分别更新。

:::

::: tip 数据库的约束类型有哪些？

- 主键（PRIMARY KEY）：唯一标识一条记录。
- 唯一（UNIQUE）：字段值不能重复。
- 非空（NOT NULL）：字段不能为空。
- 检查（CHECK）：字段必须满足条件。
- 默认（DEFAULT）：字段有默认值。
- 外键（FOREIGN KEY）：保持表之间的数据一致性。


**实际上，约束可以分为三类完整性：**

- **实体完整性：主键、非空。**
- **字段完整性：CHECK、DEFAULT、NOT NULL。**
- **参照完整性：外键。**

:::

::: tip 视图（View）的作用和优缺点是什么？

作用：提供数据安全、简化查询、提高可维护性、作为数据抽象层。

优点：安全、简化操作、结构隔离、逻辑复用。

缺点：性能差、部分视图不可更新、嵌套复杂难维护。

:::

::: tip 什么是主键、外键、候选键、超键？

- 主键（PRIMARY KEY）：唯一标识一条记录。
- 外键（FOREIGN KEY）：保持表之间的数据一致性。

在数据库中并不能直接定义“候选键”和“超键”，因为这两个概念更多是数据库理论里的抽象，用来帮助我们设计表结构和范式化

- 超键 = 唯一标识记录的所有组合（可能有冗余）。
- 候选键 = 去掉冗余后最小的超键（主键从这里挑）。

:::


### SQL

::: SQL 分为哪几类？
 SQL（Structured Query Language） 是 结构化查询语言，专门用于操作关系型数据库。
  - DDL（数据定义语言）：定义数据库对象
    - CREATE、ALTER、DROP
  - DML（数据操作语言）：操作表中数据
    - INSERT、UPDATE、DELETE
  - DQL（数据查询语言）：查询数据
    - SELECT、WHERE、GROUP BY、DISTINCT、ORDER BY、JOIN
  - DCL（数据控制语言）：权限管理
    - GRANT、REVOKE
  - TCL（事务控制语言）：事务管理
    - COMMIT、ROLLBACK、SAVEPOINT
:::

::: tip JOIN 有哪几种类型？区别是什么？

- INNER JOIN（内连接）
  - 只取匹配的数据行
  - 不匹配的行会被舍弃
- LEFT / RIGHT JOIN（外连接）
  - 保留指定表的所有记录
  - 未匹配的另一表字段填 NULL
- FULL JOIN（全外连接）
  - 保留两表所有记录
  - 左右表未匹配的字段填 NULL
- CROSS JOIN（笛卡尔积）
  - 不考虑条件，返回两表所有组合
  - 数据量可能迅速膨胀
- SELF JOIN（自连接）
  - 表与自己关联，常用于层级结构（如员工-经理关系）

.net 使用最多的是由LINQ转换的Join(内联)，GroupJoin（左连接+分组）

:::


::: tip UNION 和 UNION ALL 的区别？

UNION 合并去重，UNION ALL 合并不去重

:::

::: tip 什么是子查询？有哪些限制？

子查询是嵌套在 另一个查询语句内部的查询，可以出现在 SELECT、FROM、WHERE 等位置。

1. 返回单个值（1行1列）
   1. 如：查询字段需要再去查询
   2. 如：查询条件 = 
   3. 不返回一行一列会报错
2. 返回单列多行
   1. 通常在 IN 或 EXISTS 中使用
3. 返回一行多列
   1. 用于比较操作，例如 (col1, col2) = (subquery)。
4. 返回多行多列
   1. 子查询结果当作表来查询。
   2. 如：FROM 子查询（必须有别名）

5. 依赖外部查询（不推荐，每次查询都会调用很慢）
   1. WHERE A.ID = (SELECT MAX(B.ID) FROM B WHERE B.RefID = A.ID)
6. 不依赖外部查询（子查询独立执行一次）
   1. WHERE A.ID IN (SELECT ID FROM B)

:::

::: tip EXISTS 和 IN 的区别？

- EXISTS : 子查询是否存在行，找到第一个就退出，大数据是快
- IN ：值是否在集合中，通常先执行子查询生成集合，再做匹配，大数据时慢


:::

::: tip WHERE vs HAVING 的区别？

WHERE 作用于原始行，HAVING 作用于GROUP BY聚合后的结果。

:::

::: tip 什么是分页查询？不同数据库如何实现？

分页查询是 只查询结果集中的一部分记录，常用于前端展示列表时，每次只加载一页数据。

MySQL/PG → LIMIT OFFSET，SQL Server/Oracle → OFFSET FETCH，Oracle 老版本 → ROWNUM 子查询

LINQ 使用 Skip Take 转换

注意

- 必须要有排序，Skip/Take 对 无序集合结果不稳定，因为不同数据库返回顺序可能不同。
- 大数据会出现深分页影响效率，可以前端限制分页，对静态或变化少的数据，可预计算每页起点 ID 通过ID再查询分页

:::

::: tip Any() 和 Count() > 0对比

只判断存在性 → 用 Any()

需要总数 → 用 Count()

大表场景，千万条数据千万不要用 Count() > 0 判断存在性

:::

::: tip 什么是存储过程，如何使用

存储过程是 在数据库中预编译保存的一组 SQL 语句，可以通过名字调用，并可接受参数。

创建时用 CREATE PROCEDURE，通过 CALL 或 EXEC 调用，可以带输入/输出参数。

可以通过EFCore 映射实现在查询方法内部调用

:::

::: tip 什么是触发器，如何使用

触发器是一种 数据库对象，当对某个表执行 INSERT、UPDATE、DELETE 等操作时，会 自动触发执行的一段 SQL 代码。

创建时用 CREATE TRIGGER

:::


### 索引

::: tip 一般关系型数据库为什么用B+树，不使B树

- B树的每个结点都存储了key和data，导致查询效率不稳定，有时快有时慢，无法预估，不利于优化
- B+树的data存储在叶子节点上，查询效率稳定，一个节点就可以存储更多的key。可以使得树更矮，所以IO操作次数更少。

- B+树的所有叶结点构成一个有序链表，可以按照关键码排序的次序遍历全部记录由于数据顺序排列并且相连，所以便于区间查找和搜索。
- B树则需要进行每一层的递归遍历。 相邻的元素可能在内存中不相邻，所以缓存命中性没有B+树好。

:::

::: tip 索引是什么？索引的类型有哪些？

索引是 用于 快速定位和访问数据 一个或多个列的 数据结构 的额外维护。

按物理存储分类

- 聚集索引 (Clustered Index)
  - 每张表只有一个聚集索引，一般默认为主键
  - B+树 按索引顺序存储，范围查询/排序有关键作用
  - 如果使用UUID解决分布式主键冲突问题会导致查询速率变慢。建议使用雪花算法及时间戳 + 顺序 + 校验码
- 非聚集索引 (Non-Clustered Index)
  - 索引单独存储，数据行在表中顺序不变
  - **如果所查询的列不在索引中或者不在同一个索引中（覆盖索引），会先查到主键再回表查询**
  - **如果有索引列查询条件会优先执行查询条件再回表（索引下推），只有可下推的条件（通常是索引列上的比较或范围条件）才能应用 ICP**

按逻辑功能分类

- 主键索引（Primary Key）
  - 唯一且不允许为 NULL。
  - InnoDB 中主键索引是 聚簇索引（Clustered Index），数据行存储在叶子节点上。
- 普通索引（Index / Key）
  - 最常见的索引，没有唯一性要求。
  - 如果所查询的列不在索引中或者不在同一个索引中（覆盖索引），会先查到主键再回表查询
  - 如果有索引列查询条件会优先执行查询条件再回表（索引下推），只有可下推的条件（通常是索引列上的比较或范围条件）才能应用 ICP
- 唯一索引（Unique Key）
  - 本质上和普通索引一样
  - 保证列值唯一，但允许 NULL。
  - 适用于用户账号、邮箱等字段。
- 联合索引
  - 联合索引是对表中 多个列 建立的一个索引，索引包含这些列的组合值，用于加速多列查询。
  - 联合索引的查询必须遵循 从左到右连续使用列 的原则，否则索引无法被有效利用。因为 联合索引 是 按从左到有的顺序存到B+ 树的。
    - 如 CREATE INDEX idx_name_email_age ON Users(Name, Email, Age); WHERE Name='Alice' AND Email='a@x.com';
- 全文索引（Fulltext Index）
  - 针对大文本字段（CHAR、VARCHAR、TEXT）的分词搜索。
- 空间索引（Spatial Index）
  - 针对空间数据（GIS）。
  - 底层采用 R-Tree（矩形树）结构

:::

::: tip 索引失效的常见原因有哪些？

**索引失效的根本原因就是无法使用B+树的顺序存储特性查询**

比如：

1. 使用 LIKE 模糊匹配, 前导 %
2. 使用 !=、<> 或 NOT IN 需要全表扫描
3. 在索引列上进行函数计算或表达式操作
   1. 尽量改写为范围查询
4. 索引列算术运算
   1. 避免在索引列上加减乘除
5. 列数据类型不一致或隐式转换，无法使用顺序
6. 联合索引未遵循最左前缀原则
7. OR 条件导致索引无法使用
   1. 使用UNION代替OR
8. 索引列为空值（NULL）查询
   1. 尽量避免避免 WHERE col IS NULL

:::

### 事务，并发与锁

::: tip 什么是事务？事务的四大特性是什么？

事务（Transaction）是 数据库中一组不可分割的操作单元，要么全部成功，要么全部失败回滚，保证数据的一致性和完整性。

- 原子性（Atomicity）
  - 要么全部成功，要么全部失败
  - 回滚日志（Undo Log）实现
- 一致性（Consistency）
  - 事务完成后，数据库应该从一个一致的状态转变到另一个一致的状态。
  - 最终目标都是为了保证 一致性 (Consistency)。
- 隔离性（Isolation）
  - 多个事务并发执行时，彼此之间相互隔离，一个事务不能看到另一个事务中间状态的数据。
  - 不同隔离级别（读未提交、读已提交、可重复读、串行化）对应不同程度的隔离性。
  - 通过 锁机制 和 MVCC（多版本并发控制）。
- 持久性（Durability）
  - 事务一旦提交，其结果永久保存到数据库，即使系统宕机也不会丢失。
  - 通过 Redo Log（重做日志）

:::

::: tip 数据库隔离级别

**并发事务可能出现的问题**

1. 脏读（Dirty Read）
   1. 一个事务读到了另一个事务 未提交的数据。
2. 不可重复读（Non-Repeatable Read）
   1. 同一事务中，多次读取同一行记录，结果 不一致。
3. 幻读（Phantom Read）
   1. 同一事务中，多次执行相同的查询，结果的 行数发生变化。

**解决方案**

| 隔离级别                         | 能否脏读 | 能否不可重复读 | 能否幻读                                  | 实现方式                                             |
| -------------------------------- | -------- | -------------- | ----------------------------------------- | ---------------------------------------------------- |
| **读未提交（Read Uncommitted）** | ✅ 可能   | ✅ 可能         | ✅ 可能                                    | 直接读                                               |
| **读已提交（Read Committed）**   | ❌ 禁止   | ✅ 可能         | ✅ 可能                                    | 每次读最新版本（Oracle、SQL Server、PostgreSQL默认） |
| **可重复读（Repeatable Read）**  | ❌ 禁止   | ❌ 禁止         | ✅ 可能（InnoDB 用 MVCC 避免了大多数幻读） | MVCC + 间隙锁                                        |
| **串行化（Serializable）**       | ❌ 禁止   | ❌ 禁止         | ❌ 禁止                                    | 强制事务串行执行                                     |

:::

::: tip 一般数据库中如何使用锁盒MVCC实现各种隔离级别

MVCC（Multi-Version Concurrency Control）

- 利用 版本链（undo log） + Read View，实现读操作不加锁。
- 当事务在执行 SELECT 时，会检查记录的可见性，来自未来事务，不可见。
- 适合解决 读写并发冲突。

锁（Lock）

- InnoDB 提供 表锁 行锁（Record Lock）、间隙锁（Gap Lock）、临键锁（Next-Key Lock） 来保证事务的隔离性。
- 自增锁（Lock_Auto_Inc）插入数据时，先加自增锁，再生成自增值，再释放自增锁。避免自增值重复。

锁兼容性：

- IS 和 IS：多个事务可以在同一表上加意向共享锁（IS），它们之间没有冲突。
- IX 和 IX：多个事务可以在同一表上加意向排他锁（IX），它们之间也没有冲突。
- IS 和 IX：如果一个事务已经加了意向共享锁（IS），另一个事务可以加意向排他锁（IX），但加了 IX 锁的事务不能对行加共享锁。

**隔离级别主要是在控制“读”的行为差异，而 写操作（更新、删除、插入）本质上都需要加锁来保证一致性**

其中写操作（DML）的锁如下：

``` mermaid

graph TD
    C[事务开始]
    
    C --> E1[INSERT 插入]
    E1 --> E2[加 ***插入意向锁***]
    E2 --> E3[加 ***记录锁 X锁***]
    E3 --> E4[插入新记录]

    C --> F1[UPDATE 更新]
    F1 --> F2[加 ***记录锁 X锁***]
    F2 --> F3[加 ***间隙锁 Gap Lock***]
    F3 --> F4[加 ***临键锁 Next-Key Lock***]
    F4 --> F5[更新数据]

    C --> G1[DELETE 删除]
    G1 --> G2[加***记录锁 X锁***]
    G2 --> G3[加***间隙锁 Gap Lock***]
    G3 --> G4[加***临键锁 Next-Key Lock***]
    G4 --> G5[删除数据]

    F5 --> H[事务提交/回滚]
    G5 --> H
    E4 --> H
    
    H --> I[释放所有锁]
```

其中：

- 间隙锁 Gap Lock 可重复度隔离级别以上才插入。防止幻读同一事务前后读取行数不一样。
- 更新包含更新前查询

1. 读未提交

- 普通 SELECT 不加锁。事务可以直接读到其他事务未提交的数据（脏读）。

2. 读已提交

- 普通 SELECT 不加锁（靠 MVCC）。读到的是最新已提交数据。

3. 可重复度

- 普通 SELECT 仍然不加锁（MVCC 保证一致性）。
- UPDATE/DELETE 使用 行锁 + 间隙锁（Next-Key Lock） → 防止幻读。


4. SERIALIZABLE （可串行化）

- 所有读操作都转为加锁读（共享锁 S Lock）。

:::

::: tip 悲观锁与乐观锁的区别？实现方式？

- 悲观锁 ：假设并发冲突一定会发生，所以 先加锁再操作，防止别人同时修改。数据库用来解决DML问题的锁都是悲观锁
- 乐观锁 ：假设并发冲突很少发生，所以 先操作再验证，如果发现冲突就回滚或重试。
  - 一般业务操作中不需要额外对数据库加锁，隔离级别读已提交已经可以满足基本需求。这时候需要处理并发一般使用版本号/时间戳(EF Core有类似实现)、
  - 减少死锁概率，保证性能
  - 即使有问题，也可以通过对账发现

:::

::: tip 死锁是什么？如何避免死锁？

死锁指 两个或多个事务相互等待对方持有的资源，导致事务永远无法继续执行。

- 主流数据库（Sqlserver Mysql） 会检测死锁，并选择 牺牲一个事务回滚.

如何尽量避免：

- 统一访问顺序
- 缩短事务时间
- 合理索引
  - 减少全表扫描
  - 避免大范围扫描导致的 间隙锁冲突
  - 如果更新时需要非索引字段查询，可以先查询再通过主键更新减少死锁
- 适当降低隔离级别
  - 如果业务允许，可以使用 READ COMMITTED 读已提交 避免 Next-Key Lock 导致的死锁。
- 批量处理
  - 大量更新分批执行，减少同时占用锁的数量。
- 捕获死锁，重试事务

:::

### 分布式

::: tip 数据库分库分表(数据库分片（Sharding）)的策略有哪些？ 

Sharding = Shard（分片） + ing（动作）

- 简单理解：将一个 逻辑数据库 拆分成 多个物理数据库/表，每个数据库/表只存储总数据的一部分。
- 目的是 解决单库单表数据量大、访问压力高的问题。

1. 分库策略
   1. 按业务拆分
   2. 按功能拆分
2. 分表策略
   1. 水平分表（按行拆分）
      1. 按范围（Range）例如按日期、ID区间。
      2. 对某个字段取哈希后对表数量取模。
      3. 按时间（Time-based）
   2. 垂直分表（按列拆分）
      1. 表字段过多，某些字段访问频率低。

**EF Core中如何实现**

1. 分库使用 多DBContext
2. 分表使用 动态表名映射


可以使用三方库 ShardingCore https://github.com/dotnetcore/sharding-core
:::


::: 什么是读写分离，如何实现

- 写操作只在主库（Master）执行。
- 读操作在从库（Slave/Replica）执行。
- 主从复制 主库产生 binlog → 从库同步。


注意事项:

- 主从延迟问题
  - 从库延迟可能导致 读取旧数据。
    - 可通过：
    - 写操作后读主库。
    - 延迟敏感业务只读主库。
- 事务一致性
  - 分布式事务复杂，需要保证应用逻辑正确。
- 故障切换
  - 主库宕机 → 从库升级为主库。
  - 需要应用或中间件支持自动切换。
- 扩展性
  - 从库可以水平扩展，提高读性能。
  - 主库写性能受限，需要主库扩容或分库。

EFCore ShardingCore 实现，也可以使用MySql或SQL server代理实现

### 场景题

## Redis

### 基础

1. **什么是 Redis？为什么使用 Redis？**

   * 内存数据库，支持持久化，单线程模型，性能极高。
   * 常用于缓存、分布式锁、消息队列、排行榜等场景。

2. **Redis 支持哪些数据类型？**

   * String（字符串）
   * Hash（哈希）
   * List（列表）
   * Set（集合）
   * ZSet（有序集合）
   * Stream（流）
   * Bitmap、HyperLogLog、GEO

3. **Redis 与 Memcached 的区别？**

   * Redis 支持更多数据结构。
   * Redis 有持久化机制，Memcached 纯内存。
   * Redis 有发布订阅、Lua 脚本、事务、集群模式。

4. **Redis 单线程为什么还这么快？**

   * 基于内存操作。
   * IO 多路复用（epoll）。
   * 单线程避免了上下文切换和锁竞争。

---

### 持久化与内存管理

1. **Redis 的持久化方式？**

   * RDB（快照方式，定时持久化，适合灾备恢复）
   * AOF（日志方式，实时性好，可重写压缩）
   * 混合持久化（RDB + AOF）

2. **RDB 和 AOF 区别？**

   * RDB 恢复快，数据可能丢失几分钟。
   * AOF 恢复慢，但更安全（丢失秒级数据）。
   * AOF 文件比 RDB 大。

3. **内存淘汰策略有哪些？**

   * noeviction（默认，写满报错）
   * allkeys-lru、volatile-lru（最近最少使用）
   * allkeys-random、volatile-random（随机淘汰）
   * volatile-ttl（快过期的先淘汰）

4. **Redis 如何避免内存过大？**

   * 合理设置 `maxmemory`。
   * 使用合适的淘汰策略。
   * 控制 key 的过期时间。

---

### 事务与锁

1. **Redis 事务实现？**

   * 使用 `MULTI`、`EXEC`、`WATCH`。
   * 不支持回滚，只有语法错误才会中断。

2. **Redis 如何实现分布式锁？**

   * `SET key value NX PX time`。
   * 使用 Redlock 算法保证高可用。

3. **什么是 Redlock？**

   * 基于多个独立 Redis 实例，过半成功才算加锁成功。
   * 保证分布式场景下的锁安全性。

---

### 高可用与集群

1. **Redis 主从复制原理？**

   * 主节点全量同步 → 增量同步。
   * 从节点异步复制主节点的数据。
   * 常用于读写分离。

2. **Redis 哨兵（Sentinel）机制？**

   * 监控主节点是否宕机。
   * 自动故障转移。
   * 提供服务发现。

3. **Redis Cluster 集群模式？**

   * 水平扩展，数据分片。
   * 使用哈希槽（16384 slots）。
   * 节点间通过 Gossip 协议通信。

---

### 性能优化与问题排查

1. **缓存穿透、缓存击穿、缓存雪崩？**

   * 穿透：请求不存在的数据，导致直接打到数据库。

     * 解决：布隆过滤器、缓存空值。
   * 击穿：某个热点 key 失效，大量请求打到数据库。

     * 解决：互斥锁、逻辑过期。
   * 雪崩：大量 key 同时过期。

     * 解决：随机过期时间、限流、分布式部署。

2. **如何保证缓存与数据库一致性？**

   * Cache Aside（先操作 DB，再删除缓存）。
   * 订阅 Binlog（如 Canal）异步更新缓存。
   * 延时双删策略。

3. **如何解决 Redis 热点 key 问题？**

   * 本地缓存（Guava、Caffeine）。
   * 分片 key。
   * 使用多级缓存。

4. **Redis 常见性能瓶颈？**

   * CPU 单线程瓶颈。
   * 内存不足。
   * 网络延迟。
   * 大 key 操作阻塞。

---

### 实战场景

1. **Redis 如何实现排行榜？**

   * 使用 ZSet（有序集合）。
   * `ZADD`、`ZRANGE`、`ZREVRANGE`。

2. **Redis 如何实现延时队列？**

   * 使用 ZSet 存储任务时间戳。
   * 定时轮询取出到期任务。

3. **Redis 如何实现消息队列？**

   * List（简单队列）。
   * Pub/Sub（发布订阅，但不保证可靠性）。
   * Stream（支持消费组，可靠消息队列）。

4. **Redis 如何做分布式 Session？**

   * 使用 Redis 存储用户 Session 信息。
   * 多节点共享 Session。
